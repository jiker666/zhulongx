# Frontend Data Map

This map keeps the observability UI grounded in the runtime's single source of truth. `audit.jsonl` remains authoritative for ordered facts; `state.json` supplies the latest materialized run state.

| Backend real state | Real audit events | Existing API | Current frontend projection | Directly displayable | Smallest useful gap |
| --- | --- | --- | --- | --- | --- |
| `RunState.status`, `phase`, `turns`, `toolCalls`, `httpRequests`, `tcpSessions`, `findings`, `hypotheses`, `evidence`, `strategyRevisions`, `strategyRevisionRequired`, `lastFailure`, `appliedExperienceIds`, `lineage` | `run.started`, `run.settled`, `run.finished_by_agent`, `run.error` | `GET /v1/runs/:id`, `GET /v1/runs/:id/trace` | `MissionControl`, `CurrentAction`, graph projection | Status, phase, budgets used, findings, lineage, revision count, evidence count | Per-run configured budget/scope is not part of the current `RunState` snapshot; derive only from policy event payloads until a bounded policy projection exists. |
| `RunState.plan`, `hypotheses`, `strategyRevisions` | `plan.submitted`, `hypothesis.updated`, `decision.checkpoint`, `strategy.revised` | Trace `rawEvents` and `timeline` | Decision stream and evidence graph | Plan, hypothesis status, revision plan changes, next action/rationale, checkpoint history | A dedicated reducer for state-at-sequence is not exposed; replay UI must remain event-filtered until an equivalent pure projection is added. |

| `RunLineage` | `session.forked`, `session.resumed` | Run snapshot and trace | Parent link and fork action | Lineage link, fork boundary, inherited event count | Branch compare requires loading two run traces; no compare API exists, so keep it a future detail view. |

| Evaluation ledger manifests/attempts/metrics | Evaluation API | `/v1/evaluations` endpoints | No projection in Run Detail | Evaluation Lab can display manifest and recorded metrics only | Do not infer missing benchmark metrics; use ledger fields as-is. |

## Implementation boundaries

- Never render hidden reasoning, credentials, authorization headers, cookies, or raw image pixels. Existing server trace sanitization remains the boundary.
- Never create a fake approval action. `permission.request` is display-only unless an operator-owned resolve API is explicitly present.
- Never derive confidence, success, verification, or strategy changes from prose. Use typed state and event payloads only.
- New UI components should accept projections as props and remain pure; API calls stay in the existing run hooks.
